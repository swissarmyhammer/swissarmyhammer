title: ValidatorLoader enumerates validators in HashMap order
---
Found while investigating ^k5wsxh0.

`ValidatorLoader` keeps `rulesets: HashMap<String, RuleSet>` (`crates/swissarmyhammer-validators/src/validators/loader.rs`). Three accessors return that map's iteration order with no sort:

- `list_rulesets` — `self.rulesets.values().collect()`
- `list_ruleset_names` — `self.rulesets.keys().cloned().collect()`
- `matching_rulesets` — `self.rulesets.values().filter(..).collect()`

Rust seeds `HashMap` at random, so the order differs per process AND per map instance.

## Why it matters

The review path does not show the defect today: `match_validators_and_files` re-keys into a `BTreeMap` and `assemble_validator_work` sorts by name. But that is a downstream accident, not a property of the source. Two surfaces DO leak it:

- the `list validators` MCP op (`crates/swissarmyhammer-tools/src/mcp/tools/review/validators.rs`), whose output order changes run to run
- `swissarmyhammer_validators::match_rules`, a public API

## Work

Sort at the source. Either store the rulesets in a `BTreeMap` or sort each accessor by name.

## Acceptance

- `list_ruleset_names` returns names in sorted order.
- Two independently built loaders over the same validator set enumerate in the same order. With ~21 validators, two randomly seeded maps agreeing by chance is not a real risk, so this is a meaningful assertion rather than a tautology.
- `list validators` output order is stable across runs.
