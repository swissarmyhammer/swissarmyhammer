title: Reject a Content-Length that is larger than a fixed maximum
---
## Problem
`parse_header_line` in `crates/swissarmyhammer-lsp/src/framing.rs` parses Content-Length with `parse::<usize>()`. A negative value (`-5`) gives an error. But no maximum exists.
- `read_jsonrpc_message` in `crates/swissarmyhammer-lsp/src/daemon.rs` does `vec![0u8; length]`. A server that sends `Content-Length: 18446744073709551615` (or any very large value) can stop sah with an allocation failure.
- The sync `FrameBuffer` (client.rs) waits until `length` bytes arrive. Thus its buffer can grow with no limit.
- Also check a header line that is not UTF-8: what the async reader does with the stream after the error, and whether the sync buffer removes those bytes or stops for all time.

The Swift port session found the same problem (a negative length crashes the process there, and a bad header stops the decoder for all time).

## Fix
- Add one constant in `framing.rs`, for example `MAX_CONTENT_LENGTH` (64 MiB). The parse in `HeaderBlock` gives an error for a larger value, the same way as for a bad value. The error comes at the blank line, so the stream stays in step.
- After that error, the reader must not read the body (its length is not trusted). Thus the stream is not in step after this error. Close the connection, or mark the client as failed, so that the supervisor starts the server again. Do not read the next bytes as a header.
- A header line that is not UTF-8 must give an error, and the readers must not stop for all time or keep the bytes for all time.

## Acceptance criteria
- `Content-Length: 18446744073709551615` gives an error, and sah allocates no buffer of that size.
- `Content-Length: -5` gives an error.
- A header line that is not UTF-8 gives an error, and the buffer does not grow after it.
- The two readers (FrameBuffer and the daemon reader) act the same for each case.

## Tests
- Unit tests in `framing.rs` for each case.
- One test that sends each case to both readers. #lsp-fix #bug
