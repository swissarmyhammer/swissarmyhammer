title: function-length-swift breaks the batch on the same pre-flight readability guard
---
`builtin/validators/code-hygiene/rules/function-length-swift.md` opens with the
same pre-flight loop the three rules of `^z69hh5a` carried:

```sh
for file in "$@"; do
  if [ ! -r "$file" ]; then
    printf 'function-length-swift cannot read %s\n' "$file" >&2
    exit 1
  fi
done
```

It also exits 1 on swiftlint's own `Could not read contents of` line.

The two defects are the ones `^z69hh5a` states:

1. It breaks the WHOLE run for ONE declined path, which
   `builtin/validators/README.md` refuses.
2. `[ ! -r "$file" ]` cannot answer every refusing shape. Measured on
   `^z69hh5a`: the test is true for a path that holds no file and for a file
   with no read permission, and FALSE for a file whose bytes are not UTF-8.

`^z69hh5a` holds the worked answer for swiftlint, measured with swiftlint
0.65.0 over one healthy file beside each refusing path:

| the refusing path | status | stdout | stderr |
|---|---|---|---|
| a path that holds no file | 0 | each finding | 0 bytes |
| a file whose bytes are not UTF-8 | 0 | each finding | `Could not read contents of `<path>`` |
| a file with no read permission | 0 | each finding | the same decode line |

So `[ ! -e "$file" ]` states the path that holds no file, and a `sed`
substitution states each file swiftlint could not read, both under the
`sah-diagnostic:` marker at exit 0.

The work:

- Take the same shape `missing-docs-swift` and `magic-numbers-swift` now carry.
- Rewrite the acceptance tests
  `the_shipped_swift_function_length_tool_rule_breaks_on_a_file_it_cannot_read`
  and `..._breaks_on_a_file_it_cannot_decode` in
  `crates/swissarmyhammer-validators/src/review/tool_rules/tests/shipped/function_length_swift.rs`
  as three `declines_` tests, one for each refusing shape.
- State each measurement in the rule body.

Found while implementing `^z69hh5a`. #tool-validators #objectivity
