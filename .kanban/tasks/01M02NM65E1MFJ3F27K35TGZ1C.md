title: Delete the retired-validator mechanism entirely — deinit already clears a store
---
`mirdan` carries a whole subsystem for pruning retired validators out of a deployed `~/.validators/` or `./.validators/` store: byte-frozen snapshots of every removed rule, fixture and set, compared byte for byte, removed only on an exact match.

**`deinit` already clears a store.** The snapshot mechanism is a second, far more expensive way to reach the same end state, and it carries an ongoing tax: every rule or fixture ever deleted must be recovered from git, verified by sha256, and frozen forever, or the prune silently stops firing.

The user's decision, verbatim: *"we SHOULD NOT have 'retirement' code at all, we have deinit."*

## What to delete

- `crates/mirdan/src/retired_validators.rs` — the whole module: `RetiredFile`, `RetiredSet`, `RetiredSetFile`, `RETIRED_VALIDATOR_SETS`, `RETIRED_VALIDATOR_FILES`, `prune_unmodified_retired_sets`, `prune_unmodified_retired_files`, and their tests.
- `crates/mirdan/retired-validators/` — every byte-frozen snapshot. There are 11 set directories plus the file-grain snapshots.
- The wiring in `crates/mirdan/src/install/profile.rs`: both prune calls in `install_profile_validators`, the shared `report_pruned` helper, and the `InitEvent::Action` reporting of removed files.
- `RETIRED_FIXTURE_COUNT` and the retired-prune tests in `crates/mirdan/src/install/tests.rs`.
- The module reference in `crates/mirdan/src/lib.rs` and its doc.

## What must NOT break

- `deinit` must still clear a store completely — that is the whole premise. Verify it does, with a real run against a throwaway `HOME` holding a populated store, rather than assuming.
- `install_profile_validators` must still install correctly with the prune calls gone.
- `sah doctor` must not regress.

## Check before deleting

Confirm nothing outside `mirdan` consumes the module. `swissarmyhammer-doctor` and the validators crate both read the deployed store, so establish they do not depend on the prune having run.

## History, so this is not re-litigated

Two cards built this: `^w6ypb8b` added the file grain and `^4kzxdex` the fixture grain, both landing this session. Both are superseded by this decision rather than wrong at the time — the set-level prune predates them. The measured behaviour they established is preserved here for whoever revisits the question: an exact byte match removes the file, any user edit leaves it alone, and a store written before a rule was deleted keeps running that rule until something removes it. `deinit` is that something.

## Done when

- No `retired_validators` module, no `retired-validators/` tree, no prune call in the install path.
- `deinit` verifiably clears a populated store, measured against a throwaway HOME.
- `cargo nextest run --workspace` green; fmt and clippy clean.
