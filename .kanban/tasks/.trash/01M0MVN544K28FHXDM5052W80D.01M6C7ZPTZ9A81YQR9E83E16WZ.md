The Airbnb skill has about ten rules that NO tool can decide and that we do not have. These are real judgment rules. They belong in `builtin/validators/swift/rules/`.

Source: https://swift.airbnb.tech/skill

## The rules

Group them into new files, or add them to the closest existing file. Suggested placement:

NEW `initialization.md`
- Do no meaningful or slow work in `init()`. No database connections, no network requests, no large disk reads. Move that work to an explicit `start()`/`load()` the caller invokes.
- Prefer initializing properties at `init` time over deferring them. (Pairs with the IUO rule that moves to SwiftLint.)
- Extract complex property observers (`didSet`/`willSet`) into methods. This reduces nesting and separates side effects from the property declaration.
- Extract complex callback blocks into methods, for the same reason.

NEW `immutability.md`
- Prefer immutable values. Build a collection with `map`/`compactMap`, not by appending to a `var` accumulator.
- Prefer stored `static let` or computed `static var` over mutable stored `static var`.
- Avoid global functions. Prefer a method inside a type.

NEW `preconditions.md` — or fold into `error-handling.md`
- Validate preconditions at the start of a scope with `guard`, not `if`. This keeps the happy path unindented. (Our `optionals.md` teaches this for optional binding only; the general precondition form is missing.)
- Handle an unexpected but recoverable condition with `assert` plus production logging, not a crash and not silence.

ADD to `naming-clarity.md`
- Name event-handling functions as past-tense sentences: `didTap`, not `handleTap`. Omit the subject when it is not needed for clarity.

ADD to `value-semantics.md` or a new `swiftui.md`
- For internal SwiftUI views, declare properties `internal` so the synthesized memberwise init is usable. Keep dynamic properties (`@State`, `@StateObject`) `private`.

## Style

Match the existing rules in this bundle. Each bullet is a bold claim, then DON'T, then DO, with real Swift. Short sentences. Every rule that fires must be fixable — review is binary pass/fail, with no advisory tier. Do not add a rule you are not willing to block on.

## We have no SwiftUI content anywhere

Check this before you write: the repo has no SwiftUI guidance in any validator, partial, or rule. The one bullet above is a start, not coverage. If it grows past three bullets, make `swiftui.md` its own file.
