The stderr diagnostic carrier landed on `^m6ba1bf`. A tool-rule script now states a declined item with a stderr line opening `sah-diagnostic:` while exiting 0, and the report renders it. `builtin/validators/README.md` states the contract.

Three shipped rules decline an item today and say nothing. Each has to write the marked line.

## `missing-docs-swift`, `function-length-swift`, `magic-numbers-swift`

Each holds this branch:

```sh
if [ "$measured" -eq 0 ]; then
  if grep -qE '^Error: No lintable files found at paths:' "$work/lint.err"; then
    exit 0
  fi
  exit 1
fi
```

swiftlint judged NO file — the project `excluded:` list covers every file the run named — and the rule answers 0 findings at exit 0. That reads as a clean pass over files nothing linted. Write the marker before the `exit 0` and name the paths swiftlint refused.

Each also holds a second one:

```sh
if [ -n "$project" ] && grep -qE '^Could not read configuration:' "$work/lint.err"; then
  printf '%s\n' '<rule>: swiftlint cannot read .swiftlint.yml beside this rule. The run drops the project exclude list.' >&2
  lint "" "$@"
fi
```

That line is already a diagnostic on stderr at exit 0, and it is dropped. Give it the marker.

## Done when

- Each of the three rules writes a `sah-diagnostic:` line on both branches.
- An acceptance test drives each shipped script over a project `.swiftlint.yml` that excludes every file and holds the run to reporting the diagnostic, not to silence.
